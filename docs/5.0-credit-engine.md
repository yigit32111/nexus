# NEXUS 5.0 — dormant Credit Engine

The tested SQL was applied to production as dormant schema in migration 20261127060237_nexus_50_dormant_credit_engine. No user wallets or reservations were created; the application does not call these functions for paid access. No real payment or provider calls are enabled. The planned offer is 399 TL/month with a shared USD 5 credit budget. Monthly periods currently use UTC calendar months, not payment anniversaries.

A server-provisioned wallet is required. An atomic row lock serializes reservations, request UUIDs prevent a second provider call using the same reservation ID, and settlement is idempotent. A verified actual cost replaces the reservation; if actual cost exceeds the reservation it is recorded and the wallet blocks further reservations. Unknown cost stays reserved until trusted reconciliation; never automatically release an uncertain charge. Wallet grants are service-role only. Subscription validity and revocation, signed payment events, usage lookup/reconciliation, global cost ceiling, separate premium provider keys and real provider E2E remain prerequisites. This implementation does not guarantee an upstream provider never overcharges.

CI creates synthetic auth rows inside an isolated PostgreSQL 17 service, tests permissions and ownership, invalid amounts, replay, settlement, overage, and 20 concurrent reservations of $0.50 against a $5 wallet. It must accept 10 and refuse 10. It uses no live data, credentials, or paid API.

Live verification (2026-11-27): 12/12 public tables have RLS enabled; neither anon nor authenticated has CRUD on the credit tables or EXECUTE on the credit functions. A service-role transaction rejected unfunded reservation and unknown settlement. A synthetic authenticated identity saw zero rows in all six user-owned tables. No persistent test data was created. Paid AI remains disabled, both credit tables empty. The six no-policy advisories correspond to deliberately private tables; the presence SECURITY DEFINER and leaked-password protection warnings remain. Leaked-password protection requires Supabase Pro or above; no plan upgrade was made. Keep manual SQL as the isolated test fixture; do not reapply the already recorded migration manually.
